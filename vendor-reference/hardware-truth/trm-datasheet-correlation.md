# Research: SR1010 / ZTE ZX279133 hardware truth

## Summary

No public ZX279133/SR1010 technical reference manual (TRM), ZX279051 datasheet, or RTL8372N/RTL8373 register manual was found. The strongest hardware truth is instead the checked-in factory 2B5 DTB/runtime capture plus symbolized vendor kernel/modules, correlated with the current mainline DTS and reverse-engineered drivers; public primary sources confirm only high-level SoC/switch/flash capabilities.

The SR1010 router is a ZX279133 dual-Cortex-A53, 512 MiB system whose board networking is: SoC NPPT/PPS/IDM packet engine; two XMAC/XPCS/SerDes paths; external RTL8372N switch for four 2.5G LAN ports over a 10G CPU link; and a discrete ZX279051 2.5GBASE-T PHY on the other path. The factory SPI-NAND is unquestionably a 128 MiB Winbond part with ID `EF AA 21`, but that ID is shared/ambiguous enough that the exact W25N01 generation cannot be proved from ID alone.

## Findings

1. **Documentation status and evidence hierarchy** — No genuine public ZX279133 TRM/datasheet or ZX279051 datasheet was located. Sanechips' public material exposes ZX279125/127S/128S/131 product summaries but not a ZX279133 register manual; PSA certification is the only authoritative public ZX279133-specific description found and confirms dual Cortex-A53 plus xPON/home-gateway positioning. A purported ZX279128S hardware manual exists on Scribd, but it is not an authoritative publication and should be treated as possibly leaked/proprietary, not as a source for ZX279133 offsets. [PSA ZX279133](https://products.psacertified.org/products/zx279133) [Sanechips fixed-network products](https://www.sanechips.com.cn/en/ProductEn/WiredEn/fixedNetworkTerminalEn/index.html)

2. **Primary local evidence is reproducible and internally cross-checked** — `vendor-reference/README.md` says the official V1.0.0.2B5 image was CRC/decryption/FIT/FDT validated, its ARM64 image reconstructed with kallsyms, and its decompiled DTB round-trips byte-identically. The accepted live runtime DTB differs from the FIT DTB only in bootargs/version and enabling SFC, so the static DT address map is unusually strong evidence. The runtime also independently confirms driver bindings and loaded `np.ko`, `rtl8373_switch.ko`, `rlt8226b.ko`, and `zx279051.ko`. [Vendor evidence methodology](https://github.com/cnjn/linux-mainline-zte-zxslc-sr1010/blob/build/vendor-reference/README.md) [Factory DTS](https://github.com/cnjn/linux-mainline-zte-zxslc-sr1010/blob/build/vendor-reference/2b5/zx279133-sr1010.dts)

3. **Core SoC map (high confidence from factory DT/runtime)** — Major blocks are: GICv3 `0x00500000/0x00540000`; SPI-NAND/Denali legacy window `0x01000000` (disabled on this board); DW-MMC `0x08a00000`; LSP0 CRM `0x10d00000`; UART0 `0x10d0d000`; SFC `0x10d0f000`; GPIO banks `0x10d10000 + n*0x40` for five banks; sysctrl `0x10e00000`; TOPCRM `0x10e10000`; pinctrl `0x10e20000`; PCU `0x10e30000`; PVT `0x10e70000`; LSP1 CRM `0x14f00000`; MDIO0/1 `0x14f01000/0x14f02000`; watchdogs `0x14f09000/0x14f0a000`; efuse `0x14f11000`; USB3 `0x15010000`; GE-PHY APB `0x15400000`; RGMII `0x15900000`; PON SerDes/PLL `0x16000000/0x16010000`; Uni-SerDes `0x16100000`; PON `0x17000000`; PPS `0x18000000`; NPPT `0x19000000`; XPCS direct space `0x1a000000` (mainline additionally identifies the second PCS at `0x1b000000`). [Factory DTS](https://github.com/cnjn/linux-mainline-zte-zxslc-sr1010/blob/build/vendor-reference/2b5/zx279133-sr1010.dts) [Mainline DTSI](https://github.com/cnjn/linux-mainline-zte-zxslc-sr1010/blob/codex/sr1010-mainline/arch/arm64/boot/dts/zte/zx279133.dtsi)

4. **Clock/reset semantics are partly explicit in factory DT, not TRM-backed** — TOPCRM registers `0x10e10000..0x10e1005c` expose mux/divider/gate fields through vendor DT properties. Examples: A53 and CCI muxes at `+0x04` (two 3-bit fields at shifts 0 and 4); NAND/SD/SFC/security muxes at `+0x08`; gates at `+0x30..+0x48`; top reset at `0x10e10060`; local reset at `0x10e10070`; watchdog reset masks at syscon `0x10e10208` bits 4 and 5. Mainline deliberately models PLL roots as fixed/read-only because safe PLL/voltage programming is not established. Thus offsets/field widths are strong DT/vendor-driver evidence, while electrical/reset polarity and unused bits remain inferred. [Factory DTS](https://github.com/cnjn/linux-mainline-zte-zxslc-sr1010/blob/build/vendor-reference/2b5/zx279133-sr1010.dts) [Mainline DTSI](https://github.com/cnjn/linux-mainline-zte-zxslc-sr1010/blob/codex/sr1010-mainline/arch/arm64/boot/dts/zte/zx279133.dtsi)

5. **MDIO controller map is compact and well reconstructed** — At each `0x14f01/2xxx` controller: write data `+0x04`, read data `+0x08`, C45 register address `+0x0c`, status `+0x10` (`bit0=done`), control `+0x14`; control fields are reg/devad `[4:0]`, PHY `[9:5]`, op `[11:10]`, C22 bit12, C45 bit13, start bit14. C45 access is a separate address transaction followed by read/write, matching IEEE Clause 45 behavior. These meanings are implementation-derived, not from a public ZTE spec. [Mainline MDIO driver](https://github.com/cnjn/linux-mainline-zte-zxslc-sr1010/blob/codex/sr1010-mainline/drivers/net/mdio/mdio-zx279133.c)

6. **SFC register map and NAND transport semantics are reverse-engineered but coherent with runtime** — SFC (`0x10d0f000`) registers: control `+0x04` start bit0; trigger `+0x08`; config `+0x0c`; mode `+0x10` (data-out bit0, data-in bit1, dummy bit2, address bit4); format `+0x14`; length `+0x18`; address `+0x1c`; command `+0x20`; IRQ enable/status `+0x28/+0x30`; status `+0x2c`; FIFO status/data `+0x34/+0x38`. FIFO is 64 bytes; RX word count is `[12:8]`, TX space `[20:16]`. Mainline limits SR1010 to 25 MHz pending characterization even though factory sets controller/flash near 100/104 MHz; that is a safety policy, not evidence that hardware is only 25 MHz capable. [Mainline SFC driver](https://github.com/cnjn/linux-mainline-zte-zxslc-sr1010/blob/codex/sr1010-mainline/drivers/spi/spi-zx279133-sfc.c) [Board DTS](https://github.com/cnjn/linux-mainline-zte-zxslc-sr1010/blob/codex/sr1010-mainline/arch/arm64/boot/dts/zte/zx279133-sr1010.dts)

7. **SPI-NAND identity: geometry is certain, exact model suffix/generation is not** — Factory dmesg reads `ff,ef,ae,21` then identifies Winbond SPI NAND: 128 MiB, 128 KiB blocks, 2048-byte pages, 64-byte OOB. Runtime sysfs reports ECC strength 4 per 512-byte step. However, public W25N01GV documentation specifies ID `EF AA 21`, the same geometry, and nominal 1-bit/512-byte internal ECC; Linux MTD discussion warns `EF AA 21` is shared by W25N01G and W25N01K and recommends parameter-page probing. Therefore “Winbond 1-Gbit W25N01-class” is proven, “W25N01GV” is likely, but exact silicon and the meaning of runtime ECC=4 are unresolved (possibly vendor controller accounting or a later same-ID part). [Factory runtime dmesg](https://github.com/cnjn/linux-mainline-zte-zxslc-sr1010/blob/build/vendor-reference/sr1010-vendor-runtime/kernel/dmesg.txt) [W25N01GV datasheet mirror](https://www.pjrc.com/tmp/winbond_w25n01gv.pdf) [Linux ID ambiguity discussion](https://lists.openwall.net/linux-kernel/2022/04/15/142)

8. **Board network topology: RTL8372N, not RTL8373, is the detected switch** — Factory dmesg explicitly prints `Found switch CHIP_RTL8372N!`; mainline reads chip ID register `0x0004` and requires `(value >> 8) == 0x837270`. Board DTS maps user ports 4–7 as four 2.5G fixed links and CPU port 8 as 10GBASE-R. The factory module filename `rtl8373_switch.ko` is therefore an SDK/module-family name, not proof that the board contains RTL8373. Realtek's official public page groups RTL8372N as a highly integrated 2.5G/10G switch but does not publish its programming register table. [Factory dmesg](https://github.com/cnjn/linux-mainline-zte-zxslc-sr1010/blob/build/vendor-reference/sr1010-vendor-runtime/kernel/dmesg.txt) [Mainline switch driver](https://github.com/cnjn/linux-mainline-zte-zxslc-sr1010/blob/codex/sr1010-mainline/drivers/net/ethernet/zte/zx279133-rtl8372n.c) [Board DTS](https://github.com/cnjn/linux-mainline-zte-zxslc-sr1010/blob/codex/sr1010-mainline/arch/arm64/boot/dts/zte/zx279133-sr1010.dts) [Realtek RTL8372N product page](https://www.realtek.com/Product/ProductHitsDetail?id=4423&lang=en-GB&menu_id=419)

9. **RTL8372N host-management register map (high confidence for this firmware/revision, inferred semantics)** — The switch is tunneled through MDIO address `0x1d`: MDIO regs `0x15` control/busy (`bit2`), `0x16` 16-bit switch address, `0x17/0x18` low/high data; command `0x1b` read and `0x19` write. Internal switch regs are 32-bit. PHY indirect port: select `0x6438`, control `0x643c`, low/read data `0x6440`, data `0x6444`; busy bit0, op status `[26:24]`, commands 3 read/7 write. SerDes indirect port: ctrl `0x03f8`, read `0x03fc`, write `0x0400`; SDS select bit0, page `[6:1]`, reg `[11:7]`, write bit14, busy/start bit15. These encodings come from vendor binary reverse engineering and successful mainline use, not a public RTL8372N register manual. [Mainline switch driver](https://github.com/cnjn/linux-mainline-zte-zxslc-sr1010/blob/codex/sr1010-mainline/drivers/net/ethernet/zte/zx279133-rtl8372n.c)

10. **RTL8372N port/VLAN/L2/MIB blocks** — Important correlated offsets: port8 forced ability `0x6364` (`0x0227` used for forced 10G/full/link); status `0x63e8..0x63fc` (ability/media/speed/duplex/link); external CPU port `0x6724` low nibble=8; SDS top mode `0x7b20` with SDS1 mode `[9:5]`, submode `[20:16]`, mode value 13 for 10G USXGMII; VLAN control `0x4e14`, ingress filter `0x4e18`, PVID pairs `0x4e24..0x4e2c`, FID enable/data `0x4e38/0x4e3c`, isolation `0x50c0 + 4*port`; table engine `0x5cac`, L2 control `0x5cb0`, write data `0x5cb8..c0`, read data `0x5ccc..d4`; MIB command/data `0x0f60/64/68`. Mainline's transport VLANs 59–62 isolate ports4–7 to CPU8; this is a board/mainline transport design, not necessarily the factory VLAN policy. [Mainline switch driver](https://github.com/cnjn/linux-mainline-zte-zxslc-sr1010/blob/codex/sr1010-mainline/drivers/net/ethernet/zte/zx279133-rtl8372n.c)

11. **RTL8226B evidence does not establish a separate SR1010 board PHY** — Factory loads `rlt8226b.ko` and logs `R8226b init success`, but the same boot subsequently identifies RTL8372N and its integrated ports, while the only discrete board PHY represented in DT is ZX279051 at MDIO1 address 1. The RTL8372N driver even has a `CFG_MAC8_8221B` mode bit that it clears for this CPU-link configuration. Thus RTL8226B code is likely bundled SDK support or internal-switch PHY support, not proof of a separately populated RTL8226B. Public Linux work confirms RTL8226B/RTL8221B are related 2.5G PHYs supporting SGMII/2500BASE-X SerDes switching; full datasheets/register books remain non-public. [Factory dmesg](https://github.com/cnjn/linux-mainline-zte-zxslc-sr1010/blob/build/vendor-reference/sr1010-vendor-runtime/kernel/dmesg.txt) [Linux RTL8226B discussion](https://lists.openwall.net/netdev/2024/04/09/40)

12. **ZX279051 identity and line-status encoding are strongly established by binary behavior** — PHY ID is `0x000084b9` read twice from C45 MMD7 device-ID register; board DT uses `ethernet-phy-id0000.84b9`. Clause-22 reg 26 has link bit6 and speed/duplex code `[9:7]`: 0/1=10 half/full, 2/3=100 half/full, 4/5=1000 half/full, 6=2500 full. This encoding matches factory live transitions and drives both PHY internal Uni-SerDes and SoC XMAC/XPCS mode selection. No public datasheet was found, so the name/ID/register semantics remain reverse-engineered rather than manufacturer-documented. [ZX279051 driver](https://github.com/cnjn/linux-mainline-zte-zxslc-sr1010/blob/codex/sr1010-mainline/drivers/net/phy/zx279051.c) [Board DTS](https://github.com/cnjn/linux-mainline-zte-zxslc-sr1010/blob/codex/sr1010-mainline/arch/arm64/boot/dts/zte/zx279133-sr1010.dts)

13. **ZX279051 vendor-private APB window and calibration** — C45 MMD31 registers 18/17 hold APB address high/low; 20/19 write data; 21 trigger (`1` write, `0` read); 23/22 read data. APB register 84 gates profile load (`1024` start, `1025` commit), register 204 bit2 reports stable, and `0x400c` controls internal XPCS power (`0x0440` on, `0x0c40` off). The 49-word 1G and 2.5G Uni-SerDes profiles differ at only nine offsets. Temperature adjustment uses MMD30 `0xb626` valid value 5, MMD31 `0x002e` temperature sample, MMD31 `0x805a[9:3]` CFCTRL, apply through MMD30 `0xb616`, with analog gate `0xb60f` and trigger `0xb62a`. These labels are inferred from recovered vendor function names/control flow; exact physical units and reserved bits are unknown. [ZX279051 driver](https://github.com/cnjn/linux-mainline-zte-zxslc-sr1010/blob/codex/sr1010-mainline/drivers/net/phy/zx279051.c)

14. **NPPT/PPS/IDM map is extensive but almost wholly reverse-engineered** — DT gives a 16 MiB NPPT window at `0x19000000`, 16 MiB PPS window at `0x18000000`, and vendor logs identify IDM interrupt/reserved-memory use. Mainline recovers sub-blocks including global/init and routing (`0x0080`, `0x019c`, `0x2438`), SIPC (`0x4000/0x4010`), RED (`0x20000+`), queue manager (`0x24000+`), upstream/downstream schedulers (`0x28000/0x2c000/0x2c400/0x2c800`), UOPC (`0x30000+`), SOPC (`0x34000+`), DMA (`0x38000+`), BMU (`0x3c000+`), parser/SMMU/hash (`0x40000+`), PPU/microcode (`0x80000+`), XMAC0 `0x140000`, XMAC1 `0x180000`, and IDM `0x280000`. The functional names are supported by recovered vendor symbols such as `red_np1_config`, `red_ind_write`, `idm_init`, and live logs, but field meanings without named masks should not be generalized beyond the observed firmware sequence. [Mainline NPPT driver](https://github.com/cnjn/linux-mainline-zte-zxslc-sr1010/blob/codex/sr1010-mainline/drivers/net/ethernet/zte/zx279133.c) [Factory DTS](https://github.com/cnjn/linux-mainline-zte-zxslc-sr1010/blob/build/vendor-reference/2b5/zx279133-sr1010.dts)

15. **NPPT DMA/descriptor truths that are sufficiently corroborated for implementation** — IDM descriptors are 32 bytes (`address`, `length_flags`, six metadata words). Mainline uses 24 RX queues, active RX queue 0, RX ring 2048, free/buffer pool ring 4096, and TX queue depth 1024. IDM register base inside NPPT is `+0x280000`; interrupt mask/cause `+0x40/+0x44`, RX release `+0x88`, refill `+0x100`; TX queue0 doorbell/done `+0x80/+0x84`, with recovered formulas for higher queues. Vendor reserved-memory sizes/logs (`IDM 0xa00000`, BMU required `0xecc000`, hash `0x1000000`) match mainline's reserved regions and setup constants. These are operationally validated implementation facts, not a complete architectural specification. [Mainline NPPT driver](https://github.com/cnjn/linux-mainline-zte-zxslc-sr1010/blob/codex/sr1010-mainline/drivers/net/ethernet/zte/zx279133.c) [Factory dmesg](https://github.com/cnjn/linux-mainline-zte-zxslc-sr1010/blob/build/vendor-reference/sr1010-vendor-runtime/kernel/dmesg.txt)

16. **XMAC/XPCS path correlation** — XMAC0 is NPPT `+0x140000`, XMAC1 `+0x180000`. Common XMAC offsets: TX control `+0x0000`, RX `+0x0010`, frame `+0x0020`, mode `+0x0280`, duplex `+0x0500`, misc `+0x3400`; enable is bit0, half-duplex bit24, speed `[31:29]`. XPCS0 direct MDIO window is at `0x1a000000`; mainline identifies XPCS1 at `0x1b000000`. LAN uses 10G USXGMII/64b66b to RTL8372N CPU8; WAN/discrete PHY path dynamically uses SGMII at <=1G and 2500BASE-X at 2.5G. The factory DTS has only one broad `xpcs@1a000000` node, so splitting into two 8 MiB direct windows is a mainline inference from vendor access patterns, albeit one now encoded in functioning drivers. [Mainline DTSI](https://github.com/cnjn/linux-mainline-zte-zxslc-sr1010/blob/codex/sr1010-mainline/arch/arm64/boot/dts/zte/zx279133.dtsi) [Mainline NPPT driver](https://github.com/cnjn/linux-mainline-zte-zxslc-sr1010/blob/codex/sr1010-mainline/drivers/net/ethernet/zte/zx279133.c) [Mainline switch driver](https://github.com/cnjn/linux-mainline-zte-zxslc-sr1010/blob/codex/sr1010-mainline/drivers/net/ethernet/zte/zx279133-rtl8372n.c)

## Conflicts and cautions

- **“SR1010 datasheet” web false positive:** search engines prominently return SPARK Microsystems' unrelated SR1010 UWB radio. It has no connection to the ZTE ZXSLC SR1010 router and must be excluded.
- **RTL8373 vs RTL8372N:** module name `rtl8373_switch.ko` conflicts with runtime chip detection and chip-ID `0x837270`; hardware truth is RTL8372N.
- **RTL8226B presence:** loaded vendor module/logs are insufficient evidence of a separately populated chip; board DT and topology identify ZX279051 as the discrete PHY.
- **Switch model naming in mainline:** compatible `zte,zx279133-rtl8372n` reflects a board-coupled driver, not a generic upstream RTL8372N binding.
- **SPI-NAND ECC:** runtime `4/512` conflicts with W25N01GV public nominal `1/512`; do not claim an exact flash revision or on-die ECC mode until ONFI/parameter-page data or package marking is captured.
- **NPPT names/fields:** symbolic names recovered from kallsyms are strong clues, but many constants are only observed configuration images. Avoid calling them universal reset values or complete bit definitions.
- **Factory DTS quality:** malformed PCIe cells/nonstandard node names are known properties of the official DTB. Mainline corrections are design fixes, not evidence that the vendor DT contained those corrected semantics.

## Gaps

- Package photographs/markings or an ONFI parameter-page dump are needed to resolve the exact Winbond part and ECC discrepancy.
- A cold-boot MDIO trace or vendor SDK source would strengthen RTL8372N register semantics, especially SDS analog patches, L2 entry word layout, MIB counter ordering, and revision applicability.
- No public ZX279133 or ZX279051 TRM/datasheet was found; obtaining Sanechips/ZTE NDA documentation is the only path to authoritative reset values, reserved-bit rules, timing/electrical limits, and complete NPPT/SerDes maps.
- Local `docs/reverse-engineering/plat_132/` and `docs/mainline-network/` materially strengthen the NPPT/IDM/SerDes/XPCS correlation. They remain reverse-engineering/implementation evidence, not substitutes for an unavailable authoritative TRM.
